## 2.7 Тестування проєкту

У даному підрозділі описано процес та методику перевірки працездатності розробленого програмного продукту «Garden Simulator». Система побудована за архітектурою «клієнт-сервер», де вся бізнес-логіка та збереження даних зосереджені на серверній частині (Rust/Axum), а клієнт (Java/JavaFX) взаємодіє з нею через мережу.

### Середовище тестування
Перевірка програмного продукту проводилася у наступному середовищі:
- **Операційна система:** Linux (Ubuntu 24.04 LTS), Windows 11.
- **Платформа Java:** OpenJDK 21.
- **Платформа Rust:** Rust 1.80+ (Edition 2024).
- **Система керування базами даних (СУБД):** PostgreSQL (використовується як єдина централізована база даних на стороні сервера).
- **Інструменти збірки:** Maven (клієнт), Cargo (сервер).
- **Мережа:** Для роботи системи обов'язковим є стабільне підключення до сервера через протоколи HTTP (для авторизації) та WebSocket (для ігрового процесу в реальному часі).

### Тестування бази даних
Оскільки клієнтська частина не має власної бази даних, тестування зосереджувалося на серверній СУБД PostgreSQL:
1.  **Міграції:** Використано інструмент **SQLx Migrations** на стороні сервера. Це дозволяє автоматично застосовувати зміни структури бази даних (DDL) при розгортанні сервера.
2.  **Цілісність та обмеження:** Перевірялися коректність зв’язків `FOREIGN KEY` (наприклад, видалення користувача повинно коректно обробляти його інвентар) та унікальність полів (`UNIQUE` для email та username).
3.  **Тестові дані:** Під час розробки база даних наповнювалася набором тестових рослин, предметів та користувачів для перевірки коректності SQL-запитів репозиторіїв.

### Методи тестування програми
Для забезпечення якості застосовувалися наступні підходи:
- **Unit-тестування на стороні клієнта (JUnit 5):** Розроблено набір тестів для перевірки моделей даних та логіки відображення. Тести перевіряють, як клієнт обробляє отримані від сервера дані та чи коректно оновлюється стан UI (наприклад, у `ServerBackedInventory`).
- **Асинхронне тестування на стороні сервера (tokio::test):** Це основний метод тестування бізнес-логіки. Використано макрос `#[tokio::test]` для перевірки асинхронних функцій репозиторіїв та сервісів, що забезпечує коректну роботу з базою даних та обробку запитів користувачів.
- **Ручне тестування:** Перевірка цілісного ігрового досвіду: запуск сервера, реєстрація нового користувача через Java-клієнт, вхід у систему та виконання ігрових дій (посадка рослин, перегляд інвентарю).
- **Налагодження (Debugging):** Використання інтерактивних засобів дебагу в IDE для виявлення причин розсинхронізації станів між клієнтом та сервером.

### Логування
Система веде детальні журнали роботи:
- **Клієнтська частина:** Використовує **SLF4J**. Логуються події встановлення WebSocket-з’єднання, помилки парсингу JSON та критичні помилки інтерфейсу.
- **Серверна частина:** Використовує крейт **tracing**. Кожен вхідний запит та кожна операція з базою даних фіксуються в консолі сервера з вказанням часу та рівня важливості (INFO, WARN, ERROR).

### Перевірка критичних ситуацій та валідація
Особлива увага приділялася надійності системи в умовах помилок:
1.  **Мережеві збої:** Тестувалася поведінка клієнта при раптовому вимкненні сервера або втраті Internet-з’єднання. Програма повинна інформувати користувача про помилку зв'язку.
2.  **Валідація на сервері:** Сервер перевіряє всі вхідні дані (формат email, унікальність логіна, наявність достатньої кількості предметів в інвентарі). Клієнт отримує структуровані повідомлення про помилки, які потім виводяться користувачеві.
3.  **Безпека (JWT):** Перевірялася неможливість виконання дій без валідного токена авторизації. Спроби несанкціонованого доступу фіксуються сервером як помилки авторизації.

**Висновок:** Завдяки комбінації автоматизованих JUnit-тестів на клієнті та асинхронних тестів на сервері, було досягнуто високої стабільності продукту. Основні функції взаємодії перевірені, а виявлені дефекти усунені.
